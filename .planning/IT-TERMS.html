IT Terms — Plain English

Every technical term you'll hear at the Wednesday meeting. Read before. Know cold.

OAuth 2.0 Auth

The industry-standard way to let a third-party app access another service on your behalf — without giving it your password. You click "Connect to Salesforce", Salesforce shows you a login page, you log in, Salesforce hands the app a token (a temporary key). The app never sees your password.

📎 Analogy: When you click "Sign in with Google" on any website — that's OAuth. Same thing here.
💼 In your demo: "Each user connects their own Salesforce account. We use OAuth — the industry standard. It's the same method as signing in with Google."
Access Token / Refresh Token Auth

After OAuth login, Salesforce gives the app two things: an access token (a short-lived key, expires in ~1 hour) and a refresh token (a long-lived key used to get a new access token automatically). This means users only need to log in to Salesforce once — the app renews its own access silently.

📎 Analogy: Access token = a day pass. Refresh token = a yearly membership that issues new day passes automatically.
External Client App (Salesforce) Process

Salesforce's name for a registered third-party connection. IT creates it in Salesforce Setup in about 10 clicks. It generates two codes — a Consumer Key (public ID for the app) and a Consumer Secret (private password the app uses). Send me those two codes and the connection works.

💼 In your demo: "IT creates it in Salesforce Setup — standard process, takes about 30 minutes. They give me two codes. Done."
OAuth Scopes Auth

Specific permissions the app requests. We need three: api (lets the app call Salesforce's API), refresh_token (lets it stay logged in), and openid (identifies which user is logged in). These are the minimum needed — no admin access, no org-wide permissions.

📎 Analogy: Like ticking boxes on a permissions screen. We only tick the ones we need.
Salesforce Sandbox Process

A complete copy of the production Salesforce org used for testing. Changes in a sandbox never affect real data. Every Salesforce customer has access to at least one. The pilot runs entirely in sandbox — production is never touched until there's explicit sign-off.

💼 In your demo: "The whole pilot is in sandbox. Zero risk to production. IT can turn it off with one click."
API (Application Programming Interface) Infra

A standardised way for two software systems to talk to each other. When the app "pushes to Salesforce", it's sending a message through Salesforce's API: "Create this asset record with these field values." Salesforce processes it and sends back confirmation. No human is involved.

📎 Analogy: A waiter taking your order to the kitchen. You don't need to go to the kitchen yourself — the waiter (API) carries the message both ways.
REST API Infra

The most common type of API. Uses standard web requests (the same technology as loading a webpage). Salesforce's main API is REST-based. It's well-documented, widely used, and stable — not experimental technology.

Row Level Security (RLS) Data

A database feature that enforces access control at the record level. In this app, RLS means User A can only see their own assets and photos — they physically cannot read User B's data, even if they tried. It's enforced by the database (Supabase), not just the app code.

💼 In your demo: "Each user can only see their own data. It's enforced at the database level, not just the app — it's not bypassable."
HTTPS / TLS Infra

Encryption for data in transit. Every request between the user's browser and the server is encrypted. The padlock in the browser address bar. TLS 1.2+ is the current standard — no older, weaker versions are allowed. Handled automatically by Cloudflare for this app.

Environment Variables Infra

Secret configuration values (like API keys and passwords) stored on the server separately from the code. The app reads them at runtime but they're never embedded in the source code or visible in the browser. The Salesforce Consumer Secret, OpenAI API key, and database URL are all stored this way.

📎 Analogy: The safe behind the painting — the code knows to look there, but it's not written on the wall.
SOC 2 Type II Data

A security certification that verifies a service provider has controls in place for security, availability, and data confidentiality — and that those controls actually work over time (Type II = audited for 6+ months, not just a point-in-time check). OpenAI holds this. Supabase holds this. It's the standard IT asks for when approving third-party cloud services.

💼 If IT asks "Is OpenAI certified?": "Yes — SOC 2 Type II. Same certification we'd require from any other cloud provider."
DPA (Data Processing Agreement) Data

A formal contract between a business and a data processor defining how personal/confidential data is handled — who's responsible for what, how breaches are reported, data retention limits. OpenAI offers one. Supabase offers one. If IT requires formal data agreements before approving a cloud vendor, we can sign them.

Callback URL (Redirect URI) Auth

The page Salesforce redirects the user back to after they log in. When IT creates the External Client App, they need to add this URL to the allowed list. Our callback URL is: https://assetbookintool.com/api/auth/salesforce/callback

💼 Have this exact URL ready to give IT in writing after the meeting.
Cloudflare (CDN / Proxy) Infra

A global network that sits in front of the server and handles SSL certificates, DDoS protection, and content delivery. All traffic to assetbookintool.com goes through Cloudflare before reaching the server. SSL certificates renew automatically — no manual maintenance.

PM2 (Process Manager) Infra

Software that keeps the app running. If the app crashes or the server restarts, PM2 automatically restarts it. It's the equivalent of "start on boot" for a web app. IT doesn't need to manage it.

💼 If IT asks about uptime: "The server restarts the app automatically if anything goes wrong. IT has nothing to maintain."
