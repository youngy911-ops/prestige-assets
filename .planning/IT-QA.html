IT Q&A — Wednesday Meeting

Questions IT will ask. Know the answers cold.

Authentication & Access
"What kind of access does this need to Salesforce?"
Read and write access to the Asset object and a few custom auction objects. Each user logs in with their own Salesforce credentials — the app never uses a shared service account. Every action is tied to the person who did it, so the audit trail works exactly the same as normal Salesforce use.
Simple version: "It works through each user's own Salesforce login. Nothing bypasses the normal permission system."
"What is OAuth 2.0 Web Server Flow?"
It's the same login method used when you click "Sign in with Google" on a website. The user clicks "Connect to Salesforce", they're taken to the Salesforce login page, they log in, Salesforce sends a secure token back to the app. The app never sees the user's password — Salesforce handles all of that.
Simple version: "It's the standard Salesforce login process. Same as logging into any connected app."
"What is an External Client App?"
Salesforce's term for a third-party app connection. IT creates it in a few clicks in Salesforce Setup — it generates a Consumer Key and Consumer Secret (two codes), they send me those codes, and the connection works. It's their standard process for any new integration. Estimated time: about 30 minutes for IT.
Simple version: "A configuration IT creates in Salesforce Setup. About 30 minutes of work on their end."
"What OAuth scopes are needed?"
Three: api (access to Salesforce REST API), refresh_token (so users don't have to log in every hour), and openid (to identify which user is logged in). These are the minimum required — no admin scopes, no ability to modify org settings.
Simple version: "Standard API access for the logged-in user only. No admin permissions."
"What Salesforce objects does it write to?"
The Salesforce standard Asset object, and when needed the associated custom auction objects (spo_AssociatedAsset__c, spo_Auction__c). Read access on Account. All writes are scoped to the logged-in user's permissions — if a user doesn't have permission to edit an object in Salesforce normally, the app can't do it either.
"What happens if someone leaves and their account is deactivated?"
Their Salesforce session is automatically revoked when the account is deactivated. The app uses Salesforce's own authentication — if Salesforce says the user is gone, the app can't connect on their behalf. No separate offboarding needed.
Data & Security
"Where is the data stored?"
Photos and extracted data are stored in Supabase, hosted in Sydney (ap-southeast-2). Salesforce records stay in Salesforce's Australian instance (AUS72). Nothing is stored offshore. The AI call goes to OpenAI's API but we can enable AU data residency — images processed and stored at-rest in Australia.
Simple version: "Everything stays in Australia."
"Is our data being used to train the AI?"
No. We use OpenAI's API (the paid business version), not the free ChatGPT product. Under OpenAI's API terms, inputs and outputs are not used to train their models. Data is retained for up to 30 days for abuse monitoring only, then deleted. We can also sign a Data Processing Addendum if required.
"What encryption is used?"
All traffic is HTTPS/TLS 1.2+. The OAuth client secret is stored server-side in encrypted environment variables — never exposed to the browser. Access tokens are stored encrypted. Supabase has Row Level Security (RLS) so users can only see their own data.
"Can I see the code?"
Yes. Happy to walk IT through any part of it. The codebase is on GitHub and I can grant read access for a security review if needed. Nothing is obfuscated.
"What happens to photos after upload?"
Photos are stored in Supabase Storage (Sydney) against the user's account. They're only accessible to the user who uploaded them via Row Level Security. They're not public, not shared, and not sent to any third party except the OpenAI extraction call.
"Is OpenAI SOC 2 / ISO 27001 certified?"
Yes. OpenAI holds SOC 2 Type II certification. If required, we can also sign a DPA (Data Processing Addendum) for additional compliance coverage. Zero Data Retention agreements are available through enterprise contracts if needed.
Simple version: "Yes. And we can sign a formal data agreement if required."
Maintenance & Support
"Who maintains this if something breaks?"
Me currently. If the pilot proves value, the intention is to formalise it — document it properly and either hand it to IT or bring in a developer. The pilot review is specifically to make that decision. Right now it's a proof of concept; after the pilot we decide how to support it properly.
"What's the uptime / SLA?"
The app is hosted on a dedicated DigitalOcean server with PM2 for process management and Nginx as the reverse proxy. SSL is handled by Cloudflare — all traffic is HTTPS, certificates are managed automatically with no manual renewal. The database runs on Supabase (99.9% uptime SLA), hosted in Sydney. The server restarts the app automatically on reboot or crash.
Simple version: "Runs on our own server, restarts itself automatically if anything goes wrong. SSL is handled automatically by Cloudflare."
"What does IT actually need to do ongoing?"
Very little. After the initial sandbox setup (one-time, ~30 min), ongoing IT involvement is just: user provisioning (adding new users to a Salesforce Permission Set), and approving production rollout after the pilot. No server management, no code deployment, no on-call.
"What about Salesforce API limits?"
Slattery's current API usage is about 63,000 requests per day out of a 45.6 million limit — that's 0.14% of capacity. This app adds roughly 10 API calls per book-in. At 100 assets a week, that's about 1,000 calls per week — completely trivial. No risk of hitting limits.
Risk Questions
"What if the AI writes wrong data into Salesforce?"
There's a mandatory review step — nothing writes to Salesforce until a human confirms it. The user sees exactly what the AI extracted, can edit any field, and then explicitly saves. It cannot write automatically without a person approving it first.
"What if the connection is compromised?"
Token rotation is in place — access tokens expire and are refreshed. If a token is ever suspected compromised, IT can revoke the External Client App in Salesforce Setup with one click and all sessions immediately stop. Same process as revoking any connected app.
"Is production Salesforce at risk during the pilot?"
No. The entire pilot runs in a sandbox — a complete copy of the production org used for testing. Production isn't touched at all until after the pilot review and explicit sign-off from IT and management.
"What's the fallback if the app goes down?"
Staff fall back to the current manual process. The app doesn't replace Salesforce — it's an input tool. If it's unavailable, book-ins happen the same way they do today. No data is locked in the app; everything is in Salesforce as normal.
